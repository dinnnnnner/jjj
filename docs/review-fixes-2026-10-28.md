# 采集项目问题修复与验证记录

日期：2026 年 10 月 28 日。关联 [PR #17](https://github.com/dinnnnnner/jjj/pull/17)。

本次修复覆盖设备接入、会话停止、采样时间、并发告警、回放、控制请求和 Windows 中文编码。代码范围是合并基线 `6893e6e` 之后的 `5c794b3`、`7bcdcf3` 两个提交；数据库原有的重试和分区实现作为验证对象，不计为本次新增实现。

提交前验证通过 116 项自动化测试，以及单独执行的 4 项真实 PostgreSQL 集成测试。当前软件侧可以进入实机验收，串口、CAN 硬件和更长时间运行仍需验证。

## 设备接入与会话管理

| 问题现象 | 原因 | 修复后的行为 |
| --- | --- | --- |
| 串口读取被其他异步分支打断后，已读字节可能丢失 | 等待阻塞读取的异步任务被取消，读取结果没有保存在传输对象上 | 保留正在执行的读取任务，下一次读取继续等待并交付同一结果；关闭端口前处理待完成读取 |
| 串口自动识别成功后丢掉首帧，设备可能因重新打开端口而复位 | 探测过程消耗了有效帧，随后关闭端口，再由采集循环重新打开 | 将原连接和缓冲区直接交给采集循环，保留首帧及后续半帧；读取返回 EOF 时退出 |
| 连接挂起或进入重连等待后，停止命令无法及时生效 | 停止消息与业务命令共用队列，只有已连接的处理循环读取它 | 使用独立停止信号，连接、发送和重连等待均可被取消；最后一个会话句柄释放时也停止任务 |
| 串口暂时没有数据时，会话被当成连接故障关闭 | 没有区分读取超时与实际连接错误 | `TimedOut` 作为空闲状态继续等待 |
| 相同请求编号的第二个命令覆盖原命令；同编号遥测可能完成命令请求 | 待处理命令按编号直接覆盖，响应匹配没有排除遥测帧 | 重复编号返回 `Busy`，原命令继续等待；`0x34` 遥测不会消耗命令响应槽位 |

实现位置：[transport/mod.rs](../src/transport/mod.rs)、[session/mod.rs](../src/session/mod.rs)、[ingress/serial.rs](../src/ingress/serial.rs)。

对应回归验证包括读取取消后字节保留、首帧与半帧拼接、连接挂起时停止、重连等待时停止、释放最后一个句柄，以及重复请求和遥测编号冲突。

## 协议解析与采样时间

| 问题现象 | 原因 | 修复后的行为 |
| --- | --- | --- |
| SENT 数据前有噪声或损坏帧时，可能跳过紧随其后的有效帧 | 候选帧尚未验证就消耗整个帧；原始 nibble 超出范围时可能被掩盖 | 验证原始 nibble 和校验结果；无效候选只前移一个字节，有效后才消耗完整帧 |
| CAN 发送回显被计为轴采样 | 轴数据解码路径未排除 TX 帧 | TX 回显不再生成轴遥测 |
| CAN 时间映射回退后，曲线和采集时间倒退 | 硬件时间映射或主机接收时间可能早于上一帧 | 保证输出采集时间不小于上一帧，必要时重设映射，后续继续保留硬件时间间隔 |
| Demo 串口数据积压后，整批采样时间过于集中 | 按处理时刻给缓冲区中的每个采样计时 | 以首包末样本接收时刻为锚点，按 6250 Hz 重建时间，组间距为 160 微秒；同组轴值和告警共用采集时刻 |

实现位置：[protocol/mod.rs](../src/protocol/mod.rs)、[ingress/can.rs](../src/ingress/can.rs)、[ingress/can_clock.rs](../src/ingress/can_clock.rs)、[ingress/serial.rs](../src/ingress/serial.rs)。

CAN 绝对时间仍包含首次回调延迟；Demo 协议没有设备时间戳，因此其绝对时间是重建结果。这些修复不提供跨设备时钟同步保证。

## 告警计算与历史回放

| 问题现象 | 原因 | 修复后的行为 |
| --- | --- | --- |
| 并发处理时可能先发布解除，再发布较早的触发，留下过期活动告警 | 状态更新后先释放锁，再发布事件，两个线程的发布顺序可能交换 | 普通阈值、SENT 跳变和帧间隔告警在同一状态临界区内完成更新与发布 |
| UI 设置 CAN 阈值后，采集端没有相应检测行为 | 阈值没有完整接入采集端控制和告警计算路径 | 增加 CAN 阈值控制命令，校验有限数值和上下限；按设备、传感器维护状态，仅作用于 `CanAxis` 数据 |
| 设置失败后界面可能呈现与采集端不一致的阈值 | 缺少以控制请求成功为条件的完整应用流程 | 收到采集端成功响应后才更新 UI 已应用阈值 |
| SENT 帧间隔告警在历史查询或回放标注中缺失 | 查询条件和标注映射未包含 `sent_frame_gap_*` | 补全历史查询和回放标注路径 |
| 多路 SENT 错误只标注其中一路；普通阈值文本可能被误判为错误标志 | 路由只考虑单一标志，或使用过宽的子串匹配，例如将 `threshold_us=1500` 误认成 `s=1` | 按完整标志 token 匹配，并对所有命中的信号生成对应标注；SQL 查询同步收紧匹配边界 |

实现位置：[app/alarm_service.rs](../src/app/alarm_service.rs)、[collector_service.rs](../src/bin/collector_service.rs)、[ui_client/alarm.rs](../src/ui_client/alarm.rs)、[ui_client/records.rs](../src/ui_client/records.rs)、[ui_client/replay.rs](../src/ui_client/replay.rs)。

并发回归测试使用 4 个线程分别处理 2000 次采样，检查告警触发、解除顺序和最终活动状态。CAN 阈值测试同时验证来源隔离、设备隔离和非法配置拒绝。阈值仍保存在进程内存中，重启后需要重新设置。

## UI 稳定性与输入处理

| 问题现象 | 原因 | 修复后的行为 |
| --- | --- | --- |
| 非有限采样污染滤波器或曲线；极大角度使归一化耗时过长 | 缺少输入检查，角度归一化通过反复加减完成 | 过滤非有限值，避免超出有限 `f32` 范围的输入修改滤波状态；圆周均值使用取模归一化 |
| 设备重新开始计时后，新旧曲线直接连接 | 曲线缓冲区保留了旧时间轴 | 发现时间回退时清理旧曲线，再记录新采样 |
| 不存在的日期或过大年份被接受 | 日期组件与数值时间戳缺少完整范围校验 | 校验真实日历日期，年份限制为 1 至 9999；拒绝会导致越界的数值时间戳 |
| 回放正在加载时，从报警记录打开另一段回放会改写当前条件 | 入口未检查正在加载或导出的状态 | 等待当前操作结束后再打开；不同模式的旧加载结果不再结束当前加载状态 |
| UI 关闭后，接收线程仍反复连接或保留新建连接 | 重连和连接状态发送路径忽略接收端已断开 | 检测到 UI 通道断开后退出相应接收流程 |
| 无 UI 订阅者时，健康接口报告 UI 丢包 | 将没有订阅者导致的广播发送失败计为丢包 | 没有订阅者不再计入 `ui_drop`；实际队列溢出仍按接收端报告计数 |

实现位置：[signal/mod.rs](../src/signal/mod.rs)、[ui_client/series.rs](../src/ui_client/series.rs)、[ui_client/time.rs](../src/ui_client/time.rs)、[ui_client/events.rs](../src/ui_client/events.rs)、[ui_client/feed.rs](../src/ui_client/feed.rs)。

## 控制请求与运行配置

| 问题现象 | 修复后的行为 |
| --- | --- |
| 控制端无响应时，UI 无限等待 | UI 控制请求设置 2 秒总超时，响应最大 8 KiB，要求换行结束；失败时保留此前已应用的阈值。调用仍是同步的，超时前界面可能短暂等待 |
| 采集端持续等待不完整请求，输入长度没有上限 | 请求最大 8 KiB、必须换行结束；读取最多等待 5 秒，响应发送最多等待 1 秒 |
| 启动日志输出整份配置，包含数据库连接密码 | 改为只记录监听地址等必要信息，不再输出整份配置 |
| 队列容量为零或最大负载超过协议表示范围时，运行时出错 | 启动时校验总线与 UI 队列容量大于零，最大负载不超过 65526 字节；修复解码长度比较的溢出风险 |
| README 引用的配置示例缺失 | 恢复 `config.toml.example`，并测试示例能解析且通过校验 |
| 一键启动独立采集服务后，UI 再启动一个内嵌采集服务 | 脚本启动 UI 时设置 `DEMO2_UI_EMBED_COLLECTOR=0`，避免重复监听端口 |

实现位置：[collector_service.rs](../src/bin/collector_service.rs)、[config.rs](../src/config.rs)、[ui_client/alarm.rs](../src/ui_client/alarm.rs)、[run_demo2.ps1](../scripts/run_demo2.ps1)、[config.toml.example](../config.toml.example)。

控制请求验证覆盖分段返回成功响应、明确拒绝、无响应超时、缺少换行和超长报文。

## 中文乱码的原因与处理

乱码检查需要区分文件内容已损坏和读取时选错编码，两者处理不同。

| 位置 | 确认的原因 | 处理状态 |
| --- | --- | --- |
| `ui_client/events.rs` 的中文自检状态匹配 | 两处字符串本身已经损坏，包含私用区字符 | 已恢复正确的中文匹配，并增加中文自检结果更新测试 |
| `ingress/can.rs` 的自检结果、通过、失败文本 | 文件内容是正确 UTF-8；Windows PowerShell 5.1 默认按 GBK 读取无 BOM 文件时显示错误 | 已保存为 UTF-8 BOM；默认读取恢复正常，代码正文不变，13 项 CAN 测试通过 |
| Windows 启动脚本及子进程输出 | 脚本识别、控制台代码页和程序 UTF-8 输出不一致 | 脚本保存为 UTF-8 BOM，主窗口和工作窗口显式设置 UTF-8，子命令使用 `EncodedCommand`；已验证中文原生命令输出 |
| 本机 PostgreSQL 服务端日志 | `lc_messages` 为 `Chinese (Simplified)_China.936`；检查的同一日志文件实际包含 GBK 行和 UTF-8 行 | 已确认混合编码并生成本地 UTF-8 可读副本；未修改 PostgreSQL 全局配置或原始日志 |

项目文本扫描覆盖 62 个文件。修复后未发现替换字符、私用区字符或可识别的典型乱码模式；这一结果不等于对全部文字做过人工语义校对。

本机数据库编码为 UTF-8。真实写库测试通过正常写入路径保存中文设备名、报警名、消息和 Unicode 符号，再逐字节比较回读结果，全部一致。另抽查 `system_events`、`alarm_events` 最近各 10000 条消息，未发现替换字符或私用区异常；未据此断言全部历史记录都没有乱码。

服务端旧日志的混合编码问题不能只靠将查看器切换为 UTF-8 解决，也不能据此判断业务数据已损坏。日志副本属于本机诊断产物，未纳入 PR。

| Windows 编码 | PowerShell 5.1 默认读取、启动命令编码、中文输出和中文写库回读验证通过 |

数据库测试位于 [postgres_recovery.rs](../tests/postgres_recovery.rs)：

| 测试 | 验证内容 |
| --- | --- |
| `reconnect_preserves_capture_times_and_cross_midnight_partitions` | 中止写入连接后重试，确认采集时间不变，跨午夜的数据可写入对应分区 |
| `concurrent_startup_and_batches_preserve_samples_and_alarm_events` | 4 个写入端同时初始化，校验 1024 条采样以及告警触发、解除和系统事件 |
| `collector_process_recovers_database_connection_without_losing_feed_samples` | 启动真实采集进程，在两批数据之间中止其数据库连接；确认 512 条采样的 ACK，以及 UI 与数据库中的采集时间、数值一致 |
| `unicode_system_and_alarm_messages_round_trip_without_corruption` | 中文设备名、报警名、系统消息与 Unicode 符号写入后逐字节回读一致 |

集成测试创建独立临时数据库，仅中止该临时库内指定测试连接。断言失败或超时时清理临时库；进程级测试还清理自己的采集进程和配置目录，不启用串口或 CAN。

TCP 连续传输和编码扫描属于本轮手动诊断验证，对应辅助脚本与日志没有加入仓库，也没有配置成自动 CI。

## 复验方法

在项目根目录执行自动化测试和静态检查：

```powershell
cargo test --all-targets --no-fail-fast
cargo clippy --all-targets
git diff --check
```

数据库测试需要可用于测试的 PostgreSQL 实例和建库、删库权限。将下列占位符替换为实际的 key/value DSN，不要把个人密码提交到仓库：

```powershell
$env:DEMO2_TEST_PG_DSN = "<测试实例的 PostgreSQL key/value DSN>"
cargo test --test postgres_recovery -- --ignored
```

单独验证 CAN 逻辑或查看该文件的中文内容：

```powershell
cargo test --lib ingress::can::tests
Get-Content -Encoding UTF8 src/ingress/can.rs
```

## 待验收事项

- 串口实机连续采集、自动识别、拔插重连，以及 DTR/RTS 对具体设备的影响。
- CAN 设备、TSMaster DLL 与驱动联调，包括多通道时间戳、自检结果、发送回显和超时告警。
- 桌面 UI 的实际交互验收，以及超过一分钟的持续负载、资源占用和长时间断线恢复。
- 如需统一 PostgreSQL 后续服务日志，单独评估并调整服务端日志语言或编码策略；本次仅完成诊断。

数据库恢复沿用有界内存缓存和至少一次写入语义：停机时未落库数据可能丢失，长时间中断超过缓存容量可能丢弃数据，提交成功但响应丢失时可能出现重复记录。本次测试没有将该机制变成磁盘级持久队列。
